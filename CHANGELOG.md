# Changelog

## 0.6.1: limits pass, release 1 (quick fixes)
- Command names are matched case-insensitively (`GIT push`, `VERCEL --prod`): macOS's disk runs them as the real tools (G9).
- Arguments xargs adds count as file names only when `--` ends the command (`xargs sed -n 1p --`), since GNU tools read a file named `-i` or `--output=x` as a flag. The refusal says how (G8).
- The same for an unquoted glob: `sed -n 1p *`, `sort *` or `git log *` reads only when nothing it matches there is named like a flag (a file `-i` or `--output=x`), or after `--` (G12, found while fixing G8).
- git read commands take an argument that isn't known yet only when it can't be a flag: after `--`, starting with a literal (`HEAD~$n`), or only `$(git merge-base ...)` / `$(git rev-parse <safe flags>)` (G2).
- A setup changed since you confirmed it keeps every risky path you confirmed and skips only what the confirmed copy skipped too. Confirming keeps a copy in the data folder (G10).
- Identical refusals in one message (parallel calls) count once for "twice in a row" (G7). Allowed calls in between still don't reset it: retrying the same refused thing after a few reads is still a loop.
- Logs drop quoted and backticked text (commit subjects, plan and case text, commands) and show paths from the repo or `~` (L3).
- Reviewers and the challenger never prompt you either: what would ask (reading `.env`) is refused and goes in their findings (B9).
- Builders may link to the system's tools (`/usr/bin/node`, `/opt/homebrew/...`), never the home folder or another repo (B10). A builder's in-place edit of a file it names through a variable (`sed -i ... "$f"`) is refused like `rm "$x"` (B4).
- plan.md's `## Design` must start with the picked direction; a mention further on ("not Direction B") no longer counts (D2).
- A hook binary that's there but can't run (killed at start, refused by the system) is logged in errors.log like a missing one, and exits 1 (P6).
- Monitor commands get the changed-files check after them, like Bash (G5).
- `npx`/`bunx`/`pnpx` running the project's own tool (`node_modules/.bin`, here or above inside the repo) or with `--no-install` isn't an install (`npx tsc --noEmit`); `-p`/`--package` still is (L1).
- A case's `test:` link must be a whole word ("latest:" isn't one), and a trailing `)` or `,` isn't part of the path (L5).

## 0.6.0: design workflow, devops rules, standup (phase 3)
- Design tasks (`/plumbline:design`, `plumbline task start --design`): the brand kit and at least 3 mockup directions go in `design.md`; the user picks one on a question with header "Direction" (one option per direction, labels starting "Direction"; free text and other options aren't a pick; the latest pick wins until approval). The checkpoint is refused until a direction is picked, plan.md's `## Design` names it, and `## Real-world proof` has `ui`. A direction question can't come pre-answered, share a prompt with the checkpoint, or change an approved plan (replan first). `"parts": {"design": false}` turns it off.
- Devops: a command the approved plan lists still asks each time when it deploys, deletes, writes outside the laptop (cloud writes, production database writes, uploads) or runs on another machine (ssh, scp, rsync to a host, ansible, kubectl exec). Package runners are looked through (`npx vercel --prod`, `pnpm dlx`, `yarn <tool>`), and deploy scripts are found behind flags and workspaces (`npm --prefix infra run deploy`, `yarn workspace api deploy`), sourced or interpreted (`. ./deploy.sh`, `python deploy.py`), and in mvn/gradle/cargo/twine. Such a command not in the plan asks. Reads, dry runs and help run as listed. `"deploy_pipeline": true` in the setup refuses deploys by hand (vercel, sls, cdk, sam, fly, firebase, kubectl apply, helm, terraform apply, pulumi up, gcloud/az deploy, wrangler, docker push, ...), with or without a task. `"parts": {"devops": false}` turns both off; the 1a outside-the-laptop prompt stays.
- Standup (`/plumbline:standup`, `plumbline standup --date`): the user's own work that day from the repo they're in: its tasks and commits (their git email only), and in other repos (Plumbline's projects, sibling folders, the setup's frontend repo) only the tasks and commits on the same tickets, plus files opened there. Unrelated projects stay out. Lists open tasks for what's next; the skill adds MemPalace for the day and, on company projects, Jira (read only).
- Sprint file: `plumbline standup tracker [--set <path>]` remembers it per project (asks you; one inside a repo must be git-ignored). Edits to it always ask, and don't count as a task's change.
- Rules: devops and design sections; the task skill covers dry runs, backup checks and phone-first UI work; setup asks whether a pipeline deploys.
- A setup changed since the user confirmed it relaxes nothing: every part counts as on (the challenger, reviewers, QA, Jira, design and devops too, not only phase 3) and deploys by hand are refused until it's confirmed again. A terminal write to `.plumbline.json` asks.
- The outside-the-laptop checks for curl, wget, httpie and database clients now look at the real target host (not "localhost" anywhere in the command), read bundled and attached flags (`-XDELETE`, `-sSd`, `--json`), httpie methods and data items, and a database URI or `host=`; `curl -X GET` no longer asks. `docker image push`, `compose push` and `buildx --push` count as pushes.

## 0.5.0: builders, blind QA, tracers and tester (2b)
- Gap-review M9 closed: a git worktree is the same project as its main checkout (`ProjectRoot` reads git's `commondir`), so it sees the same setup, tasks, proof, pause flag and session binding. A plain checkout keeps its old key. Change snapshots are kept per working tree and per helper.
- Builders (`plumbline:builder`): at start Plumbline makes the builder's own copy of the repo under `.claude/worktrees/`, from the lead's code as it is (a commit of the fingerprint tree, uncommitted work included; detached, so no branch to clean up). The builder edits and runs commands only in its copy, with the usual plan rules judged there; read-only git, `plumbline run test|related|lint|build`, no commits, no questions. `plumbline builder list|merge <n>|drop <n>`: merge is a three-way `git merge-tree` and writes nothing on overlapping edits (needs git 2.38+). The copy is removed after a merge or drop, and at stop when the builder changed nothing. The finish check needs every copy merged or dropped. The lead can't edit a builder's copy.
- Blind QA (`plumbline:qa`): writes only test files (known by name) and `qa-N.md`; starts only while nothing but tests changed since the first approval (`ApprovalPrint`); can't read the builders' copies or other helpers' notes; may run `plumbline run related|test`. While it runs, the lead's code edits in the main checkout and merges are refused. Big tasks need it at the finish check (or `plumbline waive qa`, which doesn't lapse), and the report's `## Review` must say what it caught. Its test files are logged.
- Tracers (`plumbline:tracer`, sonnet, any time) and the tester (`plumbline:tester`, sonnet, while building, only `plumbline run test|related|lint|build|e2e`) are read-only.
- Workers never prompt the user: a gate's "ask" becomes a refusal for the lead to handle.
- Only the lead's own reads and searches count as opened and looked up (the user's choice): a helper's report points to the lines, and the lead opens what it quotes. Before 0.5.0 the challenger's and reviewers' reads counted too.
- A builder's command may not name a path in the project outside its copy (an `ln` source or target anywhere outside it, `make -C`, `-C../..` stuck to the flag, `go build -o`, a climb out with `../..`, any letter case), may not name files through values known only when it runs (`$d/x`, `$(...)`) in commands that write files, and runs in the foreground (no `&`, `run_in_background` or Monitor). After each of its commands Plumbline checks the main checkout, including `.git/config`, `.git/hooks` and `.git/info`: files that changed there while it ran are held for the report's "For you". The lead's own edits and merges update the running builders' baselines, so they aren't put on a builder.
- Blind QA can't search or glob from at or above the copies' folder while a copy exists (`grep -r .`, `grep -rn x` with no folder, `rg -uu`, `find .`, `cat .claude/work*/...`); the Grep tool may search above it, since it skips the git-ignored folder, but not the folder itself. QA's commands run in a known folder, name paths plainly, and don't read git's object store (`cat-file`, `fsck`, `--all`).
- Only folders named `plumbline-*` are builders' copies; Claude Code's own worktrees in `.claude/worktrees/` aren't.
- Merges write files through the repo's filters (line endings, LFS), set and clear the executable bit, and check up front that a folder replaced by a file (or the reverse) is clear, so nothing is written when it isn't. Deletions go first. A merge that fails part way lists the files already written.
- The finish check waits for running builders; `/plumbline:cancel` lists copies left on disk.
- Test files are known by name only (a `tests/`, `__tests__/`, `testdata/` or `*.Tests/` folder, or a test file name in Go, JS/TS, Python, Ruby, C/C++, and JVM/PHP/.NET/Swift classes ending in Test or Tests; `Latest.swift`, `internal/spec/` aren't). A case's `test:` file no longer counts as a test file by itself.
- Builders and QA record their last tool call: a run counts as running until 30 minutes after it, however long it works, and a run that died lets go 30 minutes after its last call. A qa waiver also ends the QA hold. A big task approved before 0.5.0 can run blind QA if no code changed since its approval.
- `IsInside`: a name starting with two dots (`./...`, `..env`) is inside its folder; only `..` climbs out.
- `SubagentStart` timeout is 120 s (making a copy checks out the repo).
- Tests: `internal/core/workers_test.go`, `TestBuilderCommands` in `cmd/plumbline/main_test.go`.

## 0.4.1: 2a hardening, before 2b
- The finish check needs a `## For you` section in report.md and every waiver the task was given (lapsed or not), and the closing chat message must have a "For you" line (at the start of a line; the heading must be exactly "For you"). Ending that message with the commit question no longer skips the check. It sends back once, then lets go; once reported, later messages aren't checked until the code changes.
- The same refusal (same rule, reason and target) twice in a row adds "stop and ask the user" to it (helpers: "put it in your findings"). A different refusal in between, or a new message from you, starts over. Logged as `repeat-block`.
- Gap-review M13 closed: each `runs.jsonl` record carries a seal made with the laptop key, and records without a valid one are skipped. Proof counts only for the task that recorded it and, for test, related, lint and build, only when it ran the saved command. Runs recorded before 0.4.1 have no seal and no longer count: run the checks again on an open task.
- The checkpoint refuses size "small" when the plan's files are a high-impact kind (the risky-path list plus the security and data reviewer signals), or when a small plan's `## Files` has a folder or a pattern instead of each file. New `plumbline task size small|normal|big --why "..."`, before approval only.
- Case tests can name the test (`test: file::name`, backticks for names with spaces). A named test that proves several cases is listed for the challenger and reviewers as a shared test.
- Disputes: the lead writes them to `<reviewer>-disputes.md`; that reviewer must run again and answer each under `## Disputes` (withdrawn or upheld). An upheld finding must be under "For you" in the report, and so must a dispute left when the reviewer has no runs left. Each reviewer reads only its own disputes file.
- The shared reviewer checklist says style is not a finding.
- Fixed (found by the fresh-eyes review, there before 0.4.1): the Monitor tool, which runs a shell command, wasn't gated at all; it now goes through the Bash gate. A Grep whose path or glob names a secret file (.env, key files) now asks like Read, since it prints matching lines. Specialists are now called for by every file the task really changed since it started (committed, staged, unstaged or new), so a folder or a pattern in `## Files` can't hide an auth or payments file.
- When Plumbline itself fails: PreToolUse is split. Searches (Grep, Glob, MemPalace, SocratiCode, Context7, Serena's look-up tools) run in a group without `onFailure: block` (`hook pre-search`); everything else stays blocking. Replaced the old matcher, which was unanchored and also blocked searches.
- Failure reports: a crash or unreadable hook input writes `~/.plumbline/crashes/<time>-<event>.txt` (event, version, where it crashed; never the tool input). The launcher checks the binary, logs to `~/.plumbline/errors.log` and exits 1 (it exited 2, which would have blocked every prompt on an unsupported laptop). The next session start reports new failures; `/plumbline:stats` counts them; reports older than 6 months are cleaned up.

## 0.4.0: phase 2a, several reviewers, Jira reading and drafts
- The one reviewer is replaced by independent reviewers: `plumbline:code-reviewer` (always; replaces `plumbline:reviewer`), `plumbline:plan-reviewer` (normal and big tasks), and specialists called for by the changed files' paths: `security-reviewer` (auth, permissions, payments, user data, secrets), `data-reviewer` (migrations, queries, models, money math), `ux-reviewer` (frontend). The plan's `## Team` must name the specialists its files call for, and can add more; a file changed outside the plan adds its specialist at the finish check.
- Every required reviewer must have reviewed the code as it is now (after a fix, all of them check again), at most 3 runs each. Findings files are `code-review-N.md`, `plan-review-N.md`, ...; a 0.3.x `reviewer` run counts as the code reviewer's.
- Reviews stay independent: in the notes folder a reviewer reads only understanding.md, plan.md and its own earlier findings (Read, Grep, Glob and terminal commands are checked; PreToolUse now also matches Grep and Glob).
- The challenger and the reviewers share one checklist, `skills/task/review-checklist.md`, instead of a copy in each agent file.
- Jira: company tasks on a ticket need a Jira read before the checkpoint (`plumbline task tool-down jira` when it can't be reached) and, at the finish check, `TICKET-123-jira-comment.md` in the notes folder: only the comment, no AI markers, no em dashes.
- Jira is draft-only: any Atlassian or Jira tool that doesn't only read (comments, transitions, edits, worklogs, Confluence pages) is refused in every state, paused included, unless the user's own latest message asks for a post; then it asks for the user's OK on the exact text, after the AI-marker and em-dash check. Helpers never post.
- Replaced: every claude.ai connector counted as look-up only. Now only Claude Docs does; Slack, Gmail, Atlassian and the others are judged by tool name, and the write verbs now include send, post, reply, comment, transition, assign, invite, share, publish, archive, close, reopen, approve, submit and schedule.
- `plumbline status` lists the reviewers the task needs. `"parts"` takes each reviewer's name and `"jira"`.

## 0.3.1: 1a hardening (gap review H1 to H8, M1 to M8, M10 to M12)
- The Bash gate parses commands with a real bash parser (mvdan.cc/sh) and fails closed: a command counts as read-only only if every part of it was understood and is on the allowlist. A command that can't be parsed, or whose command name, eval text or `sh -c` string isn't known until it runs, is refused. Replaces the hand-written splitter and the heredoc stripping, which hid the rest of a heredoc's line.
- Every rule now sees inside wrappers and shell syntax: `sh -c`, `eval`, `env`, `timeout`, `nice`, `sudo`, `xargs`, `find -exec`, `fd -x`, `trap`, `{ ...; }`, if/for/while/case, functions, subshells, `$(...)`, `<(...)`, heredocs fed to a shell, git aliases, and the command after `plumbline run proof --`.
- Read-only list: removed every way it wrote or ran code (`sed -i`/`w`/`e` and bundles like `-ni`, awk `print >`/`system()`, `sort -o`, `uniq in out`, `xxd in out`, `tree -o`, `find -fprint0`, `yq -i`, `rg --pre`, `git diff --output`, `git -c`, `go env -w`); `>&file` and `1<>file` are writes; env prefixes other than locale and colour settings make a command not read-only.
- No-verify: short-flag bundles (`-anm`), unique prefixes (`--no-verif`), `core.hooksPath`, `HUSKY=0`, `SKIP=`, `GIT_CONFIG_*` and writes to `.git/` are blocked; `-uno` is no longer read as `-n`.
- Task state and its seal are one file written through a unique temp name, so a hook never reads one without the other (this also fixes the flaky concurrent-hooks test). Tasks saved by 0.3.0 still load and move over on the next save.
- While building, terminal commands that write the user's unsaved files or risky files outside the plan are refused and held for the report, and the 3-file cap counts them; a command that changes risky files is held, and past the cap the work stops.
- One checkpoint question per prompt, and the checkpoint checks run again before an approval is recorded.
- MCP tools are gated (PreToolUse matcher `mcp__.*`): tools that change files follow the edit rules, tools that run commands follow the Bash rules, and helpers stay read-only through them.
- A session binds to a task only on a real `plumbline task start` or `adopt`; the task follows `git checkout -b`; settings and data-folder protection works by resolved path (cd tracked, case-insensitive on macOS); the paused flag is sealed (a pause from 0.3.0 has to be redone); secret reads through globs, `<`, `curl -d@`, `-F f=@` and `wget --post-file` ask first.
- Commits: pathspec commits are scanned for secrets, `--trailer` and `$(cat file)` messages are checked for AI markers, a message or option that isn't known until it runs is refused; `git revert` (without `--no-commit`), `commit-tree` and `update-ref` are blocked; `gh`, `hub` and `glab` count as outside the laptop; `git -C` and `cd` into another repo use that repo's commit rule.
- Words are read the way the shell expands them: `$'\x..'` escapes, brace lists (`git {push,x}`), zsh's `=git`, patterns in redirects. Shell variables set to known values in the same line are followed (`n=3; sed -n "${n}p"`), and each value of a `for` loop is checked as its own command; a loop body or function that may change a value makes it unknown.
- Wrappers fail closed too: an option of `sudo`, `env`, `timeout`, `nice`, `time`, `xargs` and the others that isn't known makes the command unknown (a value could otherwise be read as the command). Added `xcrun`, `noglob`, `nocorrect`, `-`, `setsid`, `unbuffer`, `taskset`, `sched`, `emulate -c`.
- Arithmetic on a value holding `$(` or a backtick, extended globs and zsh glob qualifiers are refused (they can run code). `less +cmd` and `ag --pager` aren't read-only.
- Git: setting an alias or include (`git config alias.x`, `-c include.path`) is refused, an unknown git option before the subcommand or an alias that can't be looked up is refused, and git's global config files are protected. Every commit in a line is checked, each in its own repo. `HUSKY` set to anything but 1 or true counts as skipping hooks.
- Archives extracted into, or folders copied recursively into, `~/.claude`, the data folder or a folder holding `.git` are refused. A saved command with extra redirects or env no longer counts as saved. MCP shell tools are found under any command field, and the changed-files check keeps a snapshot per repo.
- Release binaries are built with Go 1.27.4 (`toolchain` in go.mod); 1.24.7 no longer gets security fixes.
- `plumbline setup save` no longer stops the work; the approved plan's case tests are kept at approval; proof kinds are read from formatted bullets (`- **api**: ...`); `plumbline run proof` refuses commands that prove nothing (`true`, `echo`).

## 0.3.0: phase 1b, the challenger and one reviewer
- New read-only helpers `plumbline:challenger` and `plumbline:reviewer` (same model as the session), sharing one checklist; findings scored, only 80 or more reported.
- The checkpoint needs a finished challenger run on both documents and a `## Challenge note` in plan.md (normal and big tasks; at most 2 rounds).
- The finish check needs a review of the current code and a `## Review` section in a report written after it (at most 3 reviews: the first plus 2 fix rounds).
- Helpers can only read, run read-only commands, and write their own findings file; the lead can't edit those files. Helper runs are recorded by SubagentStart/SubagentStop with the code fingerprint at both ends.
- Waiting on a background helper is no longer sent back as an unproven "done".
- `parts.challenger` / `parts.reviewer` in the setup file switch them off per project.
- Fixed: `plumbline docs-dir`, `status`, `task show` and other read-only plumbline commands were refused before approval.
- Fixed: the code fingerprint could miss a same-size edit made in the same second git last indexed the file, so proof could count for code that had changed.

## 0.2.0: hands-off by default
- One checkpoint with the understanding and the plan together (header "Checkpoint"); "Checkpoint 1" stays optional for very unclear tasks.
- Nothing waits on a prompt during a task: unsaved commands before approval are refused instead of asked; while building, same-change files outside the plan are allowed and must be in the report, risky files outside the plan and your unsaved work are refused and must be under "For you".
- New plan section "## Needs your OK": packages and outside-the-laptop commands it lists run without a prompt once you approve.
- Changes outside the plan while building are reported to Claude instead of stopping the work. Real decisions are still asked right away.
- More than 3 files outside the plan stops and asks: the plan was likely wrong.
- Replaces the old per-file confirm prompt and the two-checkpoint default.

## 0.1.0: phase 1a, the core
- Task workflow with two checkpoints on Claude Code's question prompt (auto mode, no plan mode).
- Edit backstop, Bash gate, commit rule, finish check, changed-files check, user-only pause/resume/cancel/wrong.
- Recorded proof tied to the code fingerprint; baseline-aware "no new failures"; "0 tests ran" fails.
- Project and laptop setup, task logs with 6-month detail and 1-year summaries, stats.
