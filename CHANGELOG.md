# Changelog

## 0.8.1: tighter review rounds, fewer asks for harmless commands
From this session: review rounds after small fixes were full reviews every time, a must-fix could be a hunch, and several harmless commands still stopped for the user ("claude is smart enough to identify which are harmful stuff").
- Focused later rounds. A reviewer's later run is built from its last run that counted. When every file changed since then is one its `## Findings` cited (repo-relative, letter case folded; refs to plan.md and understanding.md skipped) or a test file, and none is a gate file, the note lists the changed files and gives `git diff <last tree> <this tree>`: the reviewer reviews that diff and checks its earlier findings, and the code reviewer copies its Coverage lines for unchanged files. Any other change, a plan approved again since that run, an unreadable tree or an unresolved ref gives the full fresh pass, now with the list of changed files. A rerun with no code change (disputes) says so. The challenger's note is unchanged.
- Must-fix needs a failure. A must-fix finding (any letter case, markdown or tag on the label) needs `Fails when: <input or state> -> <wrong result>`; without it the reviewer is sent back to add it or mark the finding should-fix. The checklist's must-fix-by-kind rules give their Fails when.
- An unfixed earlier finding is written again in the later run, and only each reviewer's last run decides whether the report needs the "Should-fix not fixed:" line, so one fixed in a later round no longer forces it; only items labelled should-fix under `## Findings` count, not the word elsewhere.
- `plumbline env-names <file>` lists the names in a .env-style file and runs without asking when it is run as plain `plumbline` (a path to another program named plumbline, or a PATH set on the line, asks for a secret file). It refuses other files, symlinks and hard links, tracks quotes (multi-line values are skipped), and fails closed with only a line number on any line it can't read as `NAME=`, an unclosed quote, a trailing backslash or a read error. Masking with sed or cut still asks (those can leak part of a multi-line key), and that ask now points to env-names. Left: a .env made only of key-body lines with no header would print a short piece of one.
- `helm show` from the network (an `oci://` or `https://` address, `--repo`, a repo name such as `bitnami/nginx`) and `helm search hub` are online reads like curl: not refused while planning, no Plumbline prompt, Claude Code's own mode decides. A chart folder in the repo stays a look. `docker inspect`, `helm get values` and `aws lambda get-function-configuration` stay free, as chosen.
- Harmless asks go to Claude Code: `git switch <branch>` with no flags and `git restore --staged <paths>` with uncommitted changes (git carries them along or only unstages; any other flag, a word Plumbline can't read or a folder it can't work out still asks), and continuing a task no other live session holds. Kept after the security review, because they aren't harmless: `plumbline setup sandbox` (it always lets Docker and Plumbline run outside the sandbox, so on a sandbox that is already on it loosens it), `git checkout`, `git switch -m` and `git restore --worktree` on a dirty tree (they can overwrite edits; the check now follows `git -C`), and setting the sprint file (Plumbline shows Claude that file's changed lines). Everything that can lose work, change shared settings, reach production, install, show secrets or turn a check off still asks.
- Tasks that change no files. A plan whose `## Files` is the single line `- none (commands only)` (every case "does not apply") needs no saved-check runs, baseline, blind QA, e2e or reviewers; real-world proof and the report stay. Edits are refused (replan to change files), except git-ignored files and untracked notes. It's recomputed: while a command has left a repo file changed, the full rules apply.

## 0.8.0: faster tests by default, and a recorded answer when reviews run out
From this session: a task spent about 20 minutes waiting on a 6-minute suite that ran three times, and finishing stayed blocked after the reviewers' rounds ran out.
- A passing run is reused on the same code. Before `plumbline run <check>` (and `run checks`) runs a starting-point check for a task that hasn't changed code yet, it looks for a run of the same check with the same command, checkout and ignore list, on exactly the same code (fingerprint before and after), finished within the last 6 hours, passing, not stopped or timed out, with the project's root `.env*` files unchanged (git ignores them, so the code fingerprint can't see them). A match is recorded as this task's baseline (a new record, `reused` naming the source, no files or case tests named, so it is never proof for a case) and prints "reused the passing run from <time> on the same code; nothing ran". Test, lint, build, format and typecheck only: e2e and security depend on more than the code. Not for hotfixes, and never after the task changed code. Runs from before 0.8.0 are never reused.
- Related tests are built in. With no `test_related` saved, Plumbline derives one from the test command: plain `go test` runs the changed files' packages (a change to go.mod or go.sum, a non-Go file under a Go package folder (it may be embedded), testdata, a folder that's gone or a path outside the project runs the full suite and says why; docs and other files outside any package are skipped), jest gets `--findRelatedTests`, vitest `related --run`, pytest the changed test files and the `test_<name>.py` / `<name>_test.py` files of changed modules (a module with none found, or a pytest config change, runs the full suite; other non-Python files are skipped). The derived command counts like a saved one for the related, case-test and bug-test checks. Changed files starting with `-` are passed as `./-name`, never as flags. The setup skill now tells Claude to save these commands too, and to add `-n auto` to pytest when pytest-xdist is installed.
- Go tests run in parallel. A plain `go test` command (flags `-count`, `-race`, `-v`, `-short`, `-timeout` only, no shell operators) runs packages with 40 or more tests in shards: real `go test -run '^(...)$'` processes side by side, so vet and Go's test cache stay, and tests that set env vars or swap package functions don't clash. One limit (CPUs minus 2, at most 8) covers every process, and a machine with fewer than 4 CPUs doesn't shard; smaller packages run in one plain `go test`. Output keeps one `ok`/`FAIL` line per package, so counts match a plain run. A failed shard is rescued only when it named its failing tests (`--- FAIL`), didn't panic, and its whole set of tests passes when run again alone (`-p 1 -parallel 1`); then the run passes and Plumbline names those tests as failing only in parallel. It remembers them per package and, from then on, runs them on their own after the parallel ones, so the rest stays parallel; parallel runs never turn off for a project (saving the setup again forgets the list). A crash, a panic, a data race report or a test that fails alone is always a failure, a rescued run is never reused by another task, and when the final full suite was rescued the report must say so under For you ("only in parallel"). Reruns of tests on their own always run fresh (`-count=1`), never from Go's cache. The hidden `plumbline gotest-shard` runs only a plain `go test` (never a shell) and Claude can't call it directly. Each package's result prints as soon as it finishes (a package with remembered tests prints after all parallel shards, when those tests have run). Any other command runs as saved. This repo's suite went from about 6 minutes to under 3 on a 12-CPU laptop.
- When a reviewer has used its 3 runs and the code changed after, the finish check says to ask AskUserQuestion with header "Review cap" and options "Accept as is" and "One more round". "Accept as is" counts only while a reviewer really is out of rounds and records the code's fingerprint: the capped reviews stop blocking the commit question, finish and Stop until the code changes, and the report's Review section must say "accepted as is by you". "One more round" gives each capped reviewer whose review is out of date one more run, at the start gate too, also when it was capped with open disputes; open disputes must still be listed under For you after either answer. The question must be asked on its own, with no option descriptions. A pre-answered question, one asked by a helper, other option labels or a typed answer record nothing.
- A reviewer prompt that names a changed file is no longer refused as copied text: each changed path is replaced by one placeholder word on both sides before comparing, so a pasted sentence with a path in it is still caught. Plumbline's own standard reviewer wording ("Diff base: the task's start commit, plus new files. The notes folder has the plan and understanding.") no longer counts as copied either.

## 0.7.9: Claude reviews its own diff before the reviewers
In 0.7.8's task, reviewers found hard-link and commit-wording issues in rounds 2 and 3 that the shared checklist would have caught.
- Before every reviewer run (the first and each fix round), Claude goes through `skills/task/review-checklist.md` and the project's CLAUDE.md over its own diff and writes `self-review.md` in the notes folder: `## Checked` (each changed file by its path, and what it checked) and `## Fixed` (what it fixed, or `- none`). A reviewer start is refused until the file exists and is current: when Claude writes it with the Write or Edit tool, Plumbline records the code's fingerprint and the file's hash, and the reviewer starts only while the code still matches that fingerprint (an edit, a new or deleted file, a builder merge or a blind QA test since all count) and the file is unchanged since. The refusal names the files that changed. Also refused: a self-review written from the terminal (not recorded), a symlink or a file with a second hard link, one missing either section or a bullet under it, one whose `## Checked` doesn't name every changed file by its whole path, and any start where git can't give the fingerprint or list the changed files. A rerun on unchanged code (a dispute) keeps the same self-review. Reviewers can't read it, so their reviews stay independent. A task already building when this version installs hits the refusal at its next reviewer start.
- A message (SendMessage) to a finished reviewer starts a new run of it, and now goes through the same checks as starting one with the Agent tool: the 3-run cap, disputes, a rerun that isn't needed, the self-review and the prompt check. A helper's message to a finished reviewer is refused. Messages to running helpers and to other helpers pass as before. Each allowed reviewer start leaves a one-time pass tied to the code's fingerprint (good for 2 minutes); a reviewer run that begins without one (a message addressed by name, which Plumbline can't match to a run, or any other way around the checks) is marked as not counting and told to stop. Such a run doesn't use up one of the 3 runs and isn't sent back to write findings; while Plumbline is paused, runs aren't marked. The prompt check reads the message too.
- A short CLAUDE.md in this repo lists the usual ways gate code gets bypassed (symlinks and hard links, letter case on macOS, large or binary files, renames and staged files, other worktrees, git errors that must refuse, messages that claim what didn't happen), so they're checked while writing.

## 0.7.8: notes, docs-only tasks, and closing a task on your OK
From a friction report: writing two untracked sprint notes took over an hour (a task, a 65-minute suite twice, 3 code reviews, and a typed /plumbline:cancel).
- Untracked markdown notes need no task. With no task open, the Edit and Write tools and terminal writes may create or change a `.md` or `.markdown` file that git doesn't track (a staged file counts as tracked), and the after-command check doesn't stop the work for it. Not notes: gate files (CLAUDE.md, AGENTS.md, skills, CI and lint config), anything under `skills/`, `agents/`, `commands/`, `hooks/`, `.claude/`, `.github/`, `testdata/`, `fixtures/` or `__snapshots__/`, secret files, `.txt`/`.mdx`/`.rst` files (`requirements.txt` and MDX pages are code), symlinks and files with more than one hard link, and a file whose name or path any tracked file names, other than plain notes (a `//go:embed`, a test reading it, an `@docs/x.md` import in CLAUDE.md), or that an untracked instruction file or a root CLAUDE.local.md, AGENTS.md or GEMINI.md names. When git can't answer, the write is refused as before.
- Docs-only tasks. When the plan lists only exact note paths (tracked or not), every changed file in the tree is one (by name, so large and binary files count, and so does code that was already changed when the task started), and it isn't a hotfix: the test suite isn't needed before the first edit, at commit or at the finish; e2e and blind QA don't apply; the reviewers are the code reviewer plus any the plan's Team names, and the code review keeps counting through later doc-only fixes. Lint, build, format, typecheck and security still run before and after, since a docs site's build reads docs a name search can't see. A non-note file (git-ignored ones aside) is refused with "this task is docs-only"; replan to change code. While only notes changed, a suite run still counts as the task's baseline, so a replanned task takes one before its first code edit. The checkpoint no longer makes a docs-only plan's Team name specialists for words in a doc's path. `plumbline run checks` leaves the suite out ("test: not needed (docs-only task)"), the final commit's prompt says no suite ran, and `plumbline status` says "Docs only". Known limit: markdown a test reads through a glob or a whole folder (`--doctest-glob`, `//go:embed docs/*.md`) isn't seen by the name search.
- Closing a task on your OK: Claude may ask AskUserQuestion with header "Close task" and options "Close it" and "Keep it open". "Close it" closes the session's own task in any step, the way /plumbline:cancel does, and the log records "closed at the user's answer". The note names builder copies left on disk, helpers still running and, for a building task, what the finish check still wanted, so Claude tells you what was left unchecked. The question must be asked on its own, with exactly those two options and no descriptions. A pre-answered close question, one from a helper, free text and "Keep it open" close nothing, and a close whose save fails says so. "Drop it" at the plan question and /plumbline:cancel share the same close code, and Drop now also names left builder copies.
- Not built: reusing a recent same-code suite run as a new task's baseline (your call at the plan question: every task takes its own).

## 0.7.7: past the outside-the-plan cap, Claude fixes the plan and keeps going
- More than 3 files outside the plan no longer ends the lead's turn (it was `continue:false`, offering only replan or undo). Claude gets a note instead: the plan missed these files, so add the ones that belong to this change to plan.md's `## Files` with a line on why, undo the rest, and keep going, without asking the user. The Edit and Write tools' refusal for a 4th outside file says the same: add it to the plan, then make the edit.
- While building, a write to plan.md (Write or Edit tool, or the lead's own cat, tee, echo or printf into it) adds its new `## Files` entries to the task's plan file list. It only adds. Exact files only, relative to the repo: a folder or pattern (any of `* ? [ \`, since a backslash escapes the next character in a match and `go.mo\d` would match `go.mod`), an absolute or `../` path, an existing folder named without a slash, an entry that isn't in the repo and isn't marked `(new)` (a note written as a bullet), a risky file (the setup's `risky_paths` too), a file that decides which checks run, a file that held the user's own unsaved work and a file another session changed are not added, and the note names each (risky files still join the plan only through a replan and the user's approval). Added files go on the outside-the-plan record, including ones added before they change, so the finish check still wants every one that changed on the report's "Outside the plan" list.

- A builder past the cap is still stopped and recorded "stopped by Plumbline" (0.7.6), and its copy can still be merged. Its reason now tells the lead to decide without the user: add the files to the plan and merge, or resume the builder to undo them in its copy. A builder's refusal for a 4th outside file tells it to name the file in its notes for the lead.
- The lead's cap is logged as a note, not a block; a builder's stop is still a block.

## 0.7.6: hung runs, a watcher, and halted or resumed helpers
- Every `plumbline run` has a time limit: tests and related tests get three times the saved `suite_seconds`, at least 10 minutes; every other kind, and tests with no suite time saved, 60 minutes. At the limit the run and everything it started are killed, the run is recorded as failed (exit 124, `timed_out`), and the output says it likely hangs, with its last lines. A timed-out run is never a pass, a baseline, or the `[bug]` test seen failing. Before, a hung test never returned, so Claude waited until the user asked.
- Ctrl-C, or a stop signal to `plumbline run`, is passed on to the command's whole process group, so a stopped run leaves nothing behind. A command that passes but leaves a background process holding its output is recorded with its own exit code, and that leftover process is stopped five seconds after the command ends. A command killed by a signal records 128 plus the signal, not -1. A run stopped this way is recorded as stopped and counts for nothing. A timed-out run is never a pass, a case test's proof, a starting point to compare with, or the `[bug]` test seen failing; before the first edit it still records how the checks stood (they hang), so a task whose bug is the hang isn't blocked.
- `plumbline run test` and `related` say the usual time and the limit when `suite_seconds` is saved.
- `plumbline status --watch`: a watcher Claude starts with the Monitor tool while a suite or helper runs in the background. Right after Claude starts a Plumbline helper or a `plumbline run` in the background, Plumbline tells it to start one (the task skill was already at its size limit, and this way the reminder comes at the moment it matters). It checks every 15 seconds, prints nothing while all is well, and prints one line when a run has had no output for 5 minutes (again every 5 minutes), runs past 1.5 times its usual time, or ends, and when a helper has been quiet for 10 minutes, finishes or is stopped by Plumbline. It waits up to a minute for a run started at the same moment to be recorded, then exits when nothing is left running. A run counts as running while its process or its live-output file is there (a sandboxed shell may not see the process), and a record older than its time limit counts as dead (its process id may have been reused). A run that vanished without a result is reported after a minute's grace for its final record. It reads only the last 512 KB of `runs.jsonl`. Runs record their process id, and a run's latest output time is kept in the project's `live/` folder while it runs (touched at most once a second). It is a mode of `plumbline status`, which Plumbline already treats as read-only, so it may run before approval and inside helpers' rules without a new exception.
- A helper that Plumbline halts (the outside-the-plan stop, or a change before approval) is recorded as finished, status "stopped by Plumbline", with the reason. Claude Code sends no SubagentStop after a halt, so such a builder used to count as running for up to 3 hours and its copy couldn't be merged or dropped. The merge says it was stopped and why.
- Resuming a builder reopens its run on its existing copy (new start time and session, the stop's fields cleared, same number and notes file) instead of trying to make a second copy at the same path, which failed with "already exists" and left a blocked run behind. A builder whose copy was merged or dropped still gets a new run and copy. A builder's hooks find its open run first; other helpers' hooks find their newest run, as before.
- Fixed (from 0.7.5): a builder's terminal command could change any number of files outside the plan without counting, because "back to how it was" was checked in the main checkout, where the builder's files don't exist. That check now runs only for the lead's own checkout.
- `.plumbline.json` is ignored in this repo.

## 0.7.5: the plan's file list, and undo
- The plan's `## Files` list reads the path inside backticks, so `` - `a.py`: what changes `` is `a.py`, and a trailing `:`, `,`, `;` or `.` after a bare path is dropped. Before, the first word was taken whole (`` a.py`: ``), so the planned files counted as outside the plan and the build stopped at the fourth one.
- The checkpoint refuses a `## Files` entry that isn't in the repo (on disk or in the last commit) unless it says `(new)` or "new file" after it, so a note written as a bullet ("Unused imports are removed") or a mistyped path is caught before approval, not while building. Folders and patterns aren't checked.
- A file outside the plan that is back to how it was when the task started (restored with `git checkout --`, or created and removed again) no longer counts toward the outside-the-plan stop or the report's list. Before, the undo the stop offers set the stop off again. A file changed again, not restored, still counts.
- Tasks already open keep the file list read at their approval.

## 0.3.1: 1a hardening (gap review H1 to H8, M1 to M8, M10 to M12)
- The Bash gate parses commands with a real bash parser (mvdan.cc/sh) and fails closed: a command counts as read-only only if every part of it was understood and is on the allowlist. A command that can't be parsed, or whose command name, eval text or `sh -c` string isn't known until it runs, is refused. Replaces the hand-written splitter and the heredoc stripping, which hid the rest of a heredoc's line.
- Every rule now sees inside wrappers and shell syntax: `sh -c`, `eval`, `env`, `timeout`, `nice`, `sudo`, `xargs`, `find -exec`, `fd -x`, `trap`, `{ ...; }`, if/for/while/case, functions, subshells, `$(...)`, `<(...)`, heredocs fed to a shell, git aliases, and the command after `plumbline run proof --`.
- Read-only list: removed every way it wrote or ran code (`sed -i`/`w`/`e` and bundles like `-ni`, awk `print >`/`system()`, `sort -o`, `uniq in out`, `xxd in out`, `tree -o`, `find -fprint0`, `yq -i`, `rg --pre`, `git diff --output`, `git -c`, `go env -w`); `>&file` and `1<>file` are writes; env prefixes other than locale and colour settings make a command not read-only.
- No-verify: short-flag bundles (`-anm`), unique prefixes (`--no-verif`), `core.hooksPath`, `HUSKY=0`, `SKIP=`, `GIT_CONFIG_*` and writes to `.git/` are blocked; `-uno` is no longer read as `-n`.
- Task state and its seal are one file written through a unique temp name, so a hook never reads one without the other (this also fixes the flaky concurrent-hooks test). Tasks saved by 0.3.0 still load and move over on the next save.
- While building, terminal commands that write the user's unsaved files or risky files outside the plan are refused and held for the report, and the 3-file cap counts them; a command that changes risky files is held, and past the cap the work stops.
- One checkpoint question per prompt, and the checkpoint checks run again before an approval is recorded.
- MCP tools are gated (PreToolUse matcher `mcp__.*`): tools that change files follow the edit rules, tools that run commands follow the Bash rules, and helpers stay read-only through them.
- A session binds to a task only on a real `plumbline task start` or `adopt`; the task follows `git checkout -b`; settings and data-folder protection works by resolved path (cd tracked, case-insensitive on macOS); the paused flag is sealed (a pause from 0.3.0 has to be redone); secret reads through globs, `<`, `curl -d@`, `-F f=@` and `wget --post-file` ask first.
- Commits: pathspec commits are scanned for secrets, `--trailer` and `$(cat file)` messages are checked for AI markers, a message or option that isn't known until it runs is refused; `git revert` (without `--no-commit`), `commit-tree` and `update-ref` are blocked; `gh`, `hub` and `glab` count as outside the laptop; `git -C` and `cd` into another repo use that repo's commit rule.
- Words are read the way the shell expands them: `$'\x..'` escapes, brace lists (`git {push,x}`), zsh's `=git`, patterns in redirects. Shell variables set to known values in the same line are followed (`n=3; sed -n "${n}p"`), and each value of a `for` loop is checked as its own command; a loop body or function that may change a value makes it unknown.
- Wrappers fail closed too: an option of `sudo`, `env`, `timeout`, `nice`, `time`, `xargs` and the others that isn't known makes the command unknown (a value could otherwise be read as the command). Added `xcrun`, `noglob`, `nocorrect`, `-`, `setsid`, `unbuffer`, `taskset`, `sched`, `emulate -c`.
- Arithmetic on a value holding `$(` or a backtick, extended globs and zsh glob qualifiers are refused (they can run code). `less +cmd` and `ag --pager` aren't read-only.
- Git: setting an alias or include (`git config alias.x`, `-c include.path`) is refused, an unknown git option before the subcommand or an alias that can't be looked up is refused, and git's global config files are protected. Every commit in a line is checked, each in its own repo. `HUSKY` set to anything but 1 or true counts as skipping hooks.
- Archives extracted into, or folders copied recursively into, `~/.claude`, the data folder or a folder holding `.git` are refused. A saved command with extra redirects or env no longer counts as saved. MCP shell tools are found under any command field, and the changed-files check keeps a snapshot per repo.
- Release binaries are built with Go 1.27.4 (`toolchain` in go.mod); 1.24.7 no longer gets security fixes.
- `plumbline setup save` no longer stops the work; the approved plan's case tests are kept at approval; proof kinds are read from formatted bullets (`- **api**: ...`); `plumbline run proof` refuses commands that prove nothing (`true`, `echo`).
