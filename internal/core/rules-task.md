# Plumbline rules, part 2 of 3: the task workflow

## The plumbline command (on PATH)
- `plumbline task start --title "..." --size small|normal|big --why "..." [--ticket X] [--design]` starts a task when the user asks for a change (no question first; the plan question is their stop). Run it on its own line, so the task is tied to this session. `--design` for new or changed screens (/plumbline:design): mockups and the user's pick of a direction come before the plan.
- `plumbline status` shows the step, what's proven and what's missing. `plumbline docs-dir` prints the task's notes folder.
- `plumbline run test` (full suite), `plumbline run related --files a,b`, `plumbline run lint`, `plumbline run build`, `plumbline run e2e`, and `plumbline run format|typecheck|security` when the setup saves them: Plumbline runs the saved command and records the result. Only these runs count as proof. Every commit needs each saved check (lint, build, format, typecheck, security) to pass.
- `plumbline run proof ui|api|schema -- <command>` records real-world proof. For ui, a browser screenshot of the changed screen in the local app (Claude in Chrome), taken after the last edit, is recorded too. In the browser, check with screenshots, zoom and reading the page (read_page, get_page_text, find); a page script (javascript_tool) only when nothing else shows it (Chrome asks each time). Keep scripts to reading and measuring: on real data, one that could change something (fetch, storage, cookies, click, submit, field values) also asks. On real data, give every click its note (action_summary) saying plainly what it does; a click whose note saves, sends or deletes, a click with no note, Enter and key combinations ask the user; opening a list, Escape, typing and picking a value don't. Never feed it a command that doesn't use the change (fetching a file, a unit test): say what you couldn't check.
- `plumbline task tool-down serena|context7 --reason "..."` when an optional tool is down or not needed.
- `plumbline task size small|normal|big --why "..."` before approval. The checkpoint refuses "small" for plans that change high-impact files (the user can keep one small with /plumbline:size small; never suggest it to them) and always for files that decide which checks run (CI, git hooks, test and lint config, AI instructions).
- `plumbline task replan` goes back to planning when requirements change mid-task.
- `plumbline task finish` closes the task after the report and the commit. It refuses while the task's changes aren't committed. Then ask the user whether to commit first or whether they'll commit themselves; don't guess. Ask with AskUserQuestion, header "Commit", options "Commit it" and "Leave uncommitted": after "Commit it", a commit of that same code doesn't ask them again. Ask it last, when the finish check has nothing left but the commit; it's refused before that. A commit of one part mid-task uses the header "Commit part" and the usual commit prompt. `--uncommitted` (it asks the user) is only for when they said they'll commit.
- `plumbline standup` is for /plumbline:standup (its skill has the details).
- Pause, resume, cancel, "this block was wrong", keeping a risky change small and starting a hotfix are the user's: /plumbline:pause, /plumbline:resume, /plumbline:cancel, /plumbline:wrong, /plumbline:size small, /plumbline:hotfix. To close a task on their OK: header "Close task", options "Close it", "Keep it open".
- Untracked markdown notes need no task. A task changing only such notes is docs-only: no suite, QA or e2e; a code review. When production is broken, say the user can type /plumbline:hotfix: one checkpoint, and the first commit needs the related tests and the saved checks, with the full suite and every reviewer right after it.

## Checkpoints (Claude Code's question prompt, answered by the user)
The user usually hands over the task and comes back later: research and plan without stopping, stop once at the checkpoint, then build and prove to the end without stopping (except for real decisions).
- The checkpoint (default): write `understanding.md` and `plan.md` in the notes folder, then ask once with AskUserQuestion, header "Checkpoint", options "Approve" and "Change something". Show a short version of both in chat with the file paths.
  - Needs SocratiCode + MemPalace lookups (+ Serena when existing code changes) file:line refs to files opened during this task, and understanding.md's `## Reuse`.
  - `plan.md` needs `## Files` (every file to change, one path per line, `(new)` after a file the plan creates), `## Cases` (each `- [normal|edge|refused|boundary|repeat-safe|bug|performance|failure|concurrent] ... test: path` or `does not apply, because ...`; `failure`: a dependency down, slow or returning garbage, a crash halfway; `concurrent`: two runs at once), `## Real-world proof` (`- api: ...`, `- ui: ...`, `- schema: ...` or `does not apply, because ...`), `## Needs your OK` (packages to install and commands that reach outside the laptop, each in backticks; "none" if none), the checks, and the branch. Every line decides something: "TBD", "handle edge cases" or "add appropriate validation" are refused.
  - Real choice of approaches: recommend one, plan it in full, and list the others in a few lines each.
- "Checkpoint 1" (optional): the understanding alone, only when the task is so unclear that planning first would likely be wasted.
- Never pre-answer a checkpoint. Edits are blocked until the plan is approved; before that, a command may only look: reads, saved commands, and tests or scripts that write nothing outside the scratchpad or /tmp. Git changes, installs and anything outside the laptop wait. MCP tools that change code (Serena's edit tools, a filesystem server) follow the rules for edits, and ones that run commands those for terminal commands. One whose name doesn't say it reads counts as a change until the setup's `mcp_read_tools` lists it.
- Write terminal commands out plainly: Plumbline refuses what it can't read (eval of unknown text, a command name in a variable, a shell reading a pipe), and says how to rewrite it. End xargs commands with `--` (`xargs sed -n 1p --`), and narrow a listing that feeds a file reader (`rg -l x -g '*.go' | xargs cat`). Only one checkpoint question per prompt.
- While building, nothing waits on the user except real decisions:
  - Files outside the plan that are part of the same change: allowed, list them under "Outside the plan" in the report. More than 3: the plan missed them. Don't ask; add the ones that belong to plan.md's `## Files` with why, undo the rest, keep going.
  - Risky files outside the plan (auth, payments, migrations, dependencies, config, deploy), files that decide which checks run (CI, git hooks, test and lint config, CLAUDE.md, AGENTS.md, plugin skills and agents) and the user's own unsaved work: refused. Go on with the rest; list them under "For you".
  - Packages and outside-the-laptop commands run only if they are in the approved "Needs your OK" list. Anything else: don't, and put it under "For you".
  - No code comments, in any file that has them (tests, CSS, SQL, YAML, shell too): an edit that adds one is refused. Docstrings and JSDoc count. Allowed: tool directives (`// eslint-disable-next-line`, `// @ts-expect-error`, `//go:build`, `# type: ignore`), shebangs and license headers. Existing comments may stay or go, not be reworded. Say why in the report or commit message.

## Helpers (read-only, fresh eyes)
- Challenger (`plumbline:challenger`): before the checkpoint, after understanding.md and plan.md are written. Skipped for small tasks. At most 2 rounds. Answer its findings in plan.md's `## Challenge note`; the checkpoint needs a finished challenger run and that note.
- Reviewers, after the proof and your self-review, each on its own: `plumbline:code-reviewer` always; `plumbline:plan-reviewer` for normal and big tasks; `plumbline:security-reviewer`, `plumbline:data-reviewer`, `plumbline:ux-reviewer` when the files call for them (the plan's `## Team` names them; you can add more). The finish check needs, from every one of them, a review of the code as it is now, and a `## Review` section in report.md written after the last. At most 3 runs per reviewer (the first plus 2 fix rounds), then the user decides. After a fix that only touches tests or docs, only the code reviewer runs again: the other reviews still count, and Plumbline refuses a run that isn't needed (`plumbline status` lists what is).
- Check every finding against the code before acting on it. Push back with evidence when a finding is wrong: write it to `<reviewer>-disputes.md` in the notes folder, each dispute citing the file:line of the guard, caller or test that shows it (open it first), and run that reviewer again; it answers withdrawn or upheld, and an upheld one goes under "For you".
- A reviewer's or QA's prompt says what to review (the task, the plan, the diff base), never what to find or skip ("don't flag", "already fixed"), and carries no text from other helpers' notes or the report: Plumbline refuses both.
- Builders (`plumbline:builder`) each get a copy of the repo holding your uncommitted work (QA's tests too). Bring each one in with `plumbline builder merge <n>`, never by applying its diff yourself; by hand only for the parts a merge refused.
- Helpers write only their own findings file (challenge-N.md, code-review-N.md, ...); nobody else edits those. They never ask the user and never start helpers.
