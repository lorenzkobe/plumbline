# Plumbline rules, part 2 of 3: the task workflow

## The plumbline command (on PATH)
- `plumbline task start --title "..." --size small|normal|big --why "..." [--ticket X] [--design]` starts a task when the user asks for a change (no question first; the plan question is their stop). Run it on its own line, so the task is tied to this session. `--design` for new or changed screens (/plumbline:design): mockups and the user's pick of a direction come before the plan.
- `plumbline status`: the step, what's proven, what's missing. `plumbline docs-dir`: the notes folder.
- `plumbline run test` (full suite), `plumbline run related --files a,b` (`--before-fix`: [bug] tests on approved code; no stash), and `plumbline run lint|build|e2e|format|typecheck|security` when the setup saves them: Plumbline runs and records the saved command; only these runs are proof. `plumbline run checks` runs them all (related tests while building); `--final`: the full suite once, after the last review. No suite before the first edit: a failing test run reruns on the approved code, so old failures aren't the task's. Every commit needs each saved check to pass.
- `plumbline run proof ui|api|schema -- <command>` records real-world proof. For ui, a browser screenshot of the changed screen in the local app (Claude in Chrome), taken after the last edit, is recorded too. In the browser, check with screenshots, zoom and reading the page; a page script (javascript_tool) only when nothing else shows it. Keep scripts to reading and measuring; on real data, one that could change something (fetch, storage, cookies, click, submit, field values) asks. On real data, give every click its note (action_summary) saying plainly what it does; a click whose note saves, sends or deletes, a click with no note, Enter and key combinations ask the user; opening a list, Escape, typing and picking a value don't. Never feed it a command that doesn't use the change (fetching a file, a unit test): say what you couldn't check.
- `plumbline task tool-down serena|context7 --reason "..."`: an optional tool is down or not needed.
- `plumbline task size small|normal|big --why "..."` before approval. The checkpoint refuses "small" for plans that change high-impact files (the user can keep one small with /plumbline:size small; never suggest it to them) and always for files that decide which checks run (CI, git hooks, test and lint config, AI instructions).
- `plumbline task replan`: back to planning when requirements change.
- `plumbline task finish` closes the task after the report and the commit, and refuses while its changes are uncommitted. So ask the user whether to commit first or whether they'll commit themselves, last: AskUserQuestion, header "Commit", options "Commit it" and "Leave uncommitted"; after "Commit it", that same code commits without asking again. After "Approve and commit when green", skip it: commit once the finish check is empty. Mid-task, one part: header "Commit part". `--uncommitted` (it asks the user) only when they'll commit.
- `plumbline standup` is for /plumbline:standup.
- Pause, resume, cancel, "this block was wrong", keeping a risky change small and starting a hotfix are the user's: /plumbline:pause, /plumbline:resume, /plumbline:cancel, /plumbline:wrong, /plumbline:size small, /plumbline:hotfix. To close a task on their OK: header "Close task", options "Close it", "Keep it open".
- Untracked notes need no task or approval. A task changing only such notes is docs-only: no suite, QA or e2e; a code review. ## Files `- none (commands only)`: no checks or review; edits need replan. Production broken: suggest /plumbline:hotfix (one checkpoint, a fast first commit, then suite and reviewers).

## Checkpoints (Claude Code's question prompt, answered by the user)
The user usually hands over the task and comes back later: plan without stopping, stop once at the checkpoint, then build and prove to the end (stopping only for real decisions).
- The checkpoint (default): write `understanding.md` and `plan.md` in the notes folder, then ask once with AskUserQuestion, header "Checkpoint", options "Approve", "Approve and commit when green", "Change something", "Drop it". Show a short version in chat.
  - Needs SocratiCode + MemPalace lookups (+ Serena when existing code changes) file:line refs to files opened during this task, and understanding.md's `## Reuse`.
  - `plan.md` needs `## Files` (every file to change, one path per line, `(new)` after a file the plan creates), `## Cases` (each `- [normal|edge|refused|boundary|repeat-safe|bug|performance|failure|concurrent] ... test: path` or `does not apply, because ...`; `failure`: a dependency down or returning garbage, a crash halfway; `concurrent`: two runs at once), `## Real-world proof` (`- api: ...`, `- ui: ...`, `- schema: ...` or `does not apply, because ...`), `## Needs your OK` (packages to install and commands that reach outside the laptop, each in backticks; "none" if none), `## Guards loosened` (each check loosened or new unasked path: its file:line and every shape reaching it; or "none"), the checks, and the branch. Every line decides something: "TBD", "handle edge cases" or "add appropriate validation" are refused.
  - A real choice of approaches: plan your pick in full, the others in a few lines each.
- "Checkpoint 1" (optional): the understanding alone, only when the task is too unclear to plan yet.
- Never pre-answer a checkpoint. Edits are blocked until the plan is approved; before that, a command may only look: reads, saved commands, and tests or scripts that write nothing outside the scratchpad or /tmp. Git changes, installs and anything outside the laptop wait. MCP tools that change code (Serena's edit tools) or run commands follow the rules for edits or terminal commands. One whose name doesn't say it reads counts as a change until the setup's `mcp_read_tools` lists it.
- Write terminal commands out plainly: Plumbline refuses what it can't read (eval, a command name in a variable, a shell reading a pipe) and says how to rewrite it. End xargs commands with `--`, and narrow a listing that feeds a file reader (`rg -l x -g '*.go' | xargs cat`). Only one checkpoint question per prompt.
- While building, nothing waits on the user except real decisions:
  - Files outside the plan that are part of the same change: allowed, list them under "Outside the plan" in the report. More than 3 (test files don't count): the plan missed them. Don't ask; add the ones that belong to plan.md's `## Files` with why, undo the rest, keep going.
  - Risky files outside the plan (auth, payments, migrations, dependencies, config, deploy), files that decide which checks run (CI, git hooks, test and lint config, CLAUDE.md, AGENTS.md, plugin skills and agents) and the user's own unsaved work: refused. Go on with the rest; list them under "For you".
  - Packages and outside-the-laptop commands run only if they are in the approved "Needs your OK" list. Anything else: don't, and put it under "For you".
  - No new code comments in any file (tests, CSS, SQL, YAML, shell too; docstrings count): an edit adding one is refused. Tool directives (`// eslint-disable-next-line`, `//go:build`), shebangs and license headers are fine. Existing comments may stay or go, not be reworded. Say why in the report or commit message.

## Helpers (read-only, fresh eyes)
- Challenger (`plumbline:challenger`): before the checkpoint, after understanding.md and plan.md are written; skipped for small tasks; at most 2 rounds. The checkpoint needs its finished run and plan.md's `## Challenge note` answering it.
- Guard reviewer (`plumbline:guard-reviewer`): before the checkpoint when `## Guards loosened` isn't "none", any size; answer it in the challenge note.
- Reviewers, once tests pass (`plumbline run checks`) and after your self-review (fix rounds: `## Reach`), each on its own: `plumbline:code-reviewer` always; `plumbline:plan-reviewer` when a file that decides which checks run changes; `plumbline:security-reviewer`, `data-reviewer`, `ux-reviewer` when non-test files call for them. The finish check needs each one's review of the code as it is now, and report.md's `## Review` written after the last. At most 3 runs per reviewer; past that, after a code change or with disputes open, run `plumbline:arbiter`. If a must-fix stays open, ask: header "Review cap", options "Accept as is", "One more round", descriptions `""`. After a tests- or docs-only fix only the code reviewer reruns; a clean specialist keeps its review after a fix in cited files.
- Check every finding against the code before acting on it. Push back with evidence when a finding is wrong: write it to `<reviewer>-disputes.md`, each dispute citing the file:line of the guard, caller or test that shows it (open it first), and run that reviewer again; it answers withdrawn or upheld, and an upheld one goes under "For you".
- A reviewer's or QA's prompt says what to review, never what to find or skip ("don't flag", "already fixed"), and copies nothing from other helpers' notes or the report: Plumbline refuses both.
- Builders (`plumbline:builder`) each get a copy of the repo holding your uncommitted work (QA's tests too). Bring each one in with `plumbline builder merge <n>`, never by applying its diff yourself; by hand only for the parts a merge refused.
- Helpers write only their own findings file (challenge-N.md, code-review-N.md, ...); nobody else edits those. They never ask the user and never start helpers.
