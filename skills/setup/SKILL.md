# Plumbline setup

Work through both parts. Ask everything you can't find out yourself in one message, each question with your suggestion. Plain words. No task is open during setup, so you can't edit files: anything in the repo that needs changing becomes a task to offer at the end.

## Part 1: this laptop (skip what's already done; `plumbline setup show` and the checks below tell you)
`plumbline setup show` prints the laptop's state (built-in memory, AI attribution, the CLAUDE.md rule, the secret deny rules). Claude Code's settings files are protected, so don't try to read them.

Run these checks in parallel. One fix attempt per tool, then ask the user.
1. **MemPalace and SocratiCode** (required): call one cheap tool on each (for example a search). If one is missing, look up its current install steps online (don't go from memory), show them, and ask before installing.
2. **Serena** (exact lookups): check it responds. If missing, look up the current Serena docs and add it at user scope with `claude mcp add` (a confirm prompt appears). Use the context Serena provides for Claude Code, so tools Claude Code already has are turned off, and turn Serena's own memory tools off. MemPalace is the only memory. Serena 2 offers one `serena_repl` tool that runs Python by default; Plumbline refuses it, since it can't check what the Python does. Add Serena with `--agent-interface tools` so its own tools (`find_symbol`, ...) are there; if it's installed with only `serena_repl`, remove it and add it again with that flag.
3. **Context7** (library docs): same as Serena. It only ever sees library names and general questions, never company code.
4. **Docker** (required): `docker info`. If it's not running, try to start it once (`open -a Docker` on macOS). If it isn't installed, the user installs it.
5. **ui-ux-pro-max** (design): check whether the skill is installed; if not, ask before installing it (look up current steps).
6. **Claude Code settings**: ask whether to turn off Claude Code's built-in memory and its AI attribution on commits, whether to add the "ask before starting a task" rule to the global CLAUDE.md, and whether Claude Code should skip `.env` and key files entirely. If yes, run `plumbline setup laptop --memory-off --attribution-off --claude-md --deny-secrets` (only the parts they said yes to). It records the old values; `plumbline setup undo-laptop` puts them back (it removes only the deny rules Plumbline added).
   - `--deny-secrets` adds `Read(**/.env)`, `Read(**/*.pem)` and the like to `permissions.deny` in the user settings. Pros: Claude Code itself skips those files for Read, Grep and Glob, folder-wide searches included, and for the file commands it knows in Bash. Cons: Claude can't read them even when the user would allow it (to debug production the user looks at the values themselves), a venv folder named `.env` is skipped too, and rules can't make exceptions, so less common names (`.env.qa`) aren't in the list and keep Plumbline's own prompt.

## Part 2: this project
1. If `.claude/gate.json` exists (done-gate), read its test commands, risky paths and UI paths first so you don't ask again.
2. Learn, by reading the repo (package files, Makefile, CI config, docker-compose, README):
   - company or personal project (ask)
   - stack, test command, a related-tests command (with `{files}` where the changed files go, if the test runner supports it), lint, build, how to run the app, how to start the local database, the e2e command (Playwright) if any, optional format, typecheck and security checks (`prettier --check .`, `tsc --noEmit`, `npm audit --audit-level=high`, `govulncheck ./...`) if the project has them, and how to install dependencies without changing the lockfile (for builders' copies)
   - base branch: run `git fetch` and `git branch -r`, suggest develop or dev (company) or main (personal), ask to confirm
   - Docker database: look for a compose setup; none, or it can't be committed: ask
   - frontend repo for full-stack tickets: ask which folder
   - how deploys happen (pipeline, manual command, which branch deploys where); unclear: ask. If a pipeline deploys, save `"deploy_pipeline": true`: Plumbline then refuses deploys by hand
   - how production is reached (tunnel or credentials): ask. Save the method only, never a value
   - whether the app run on this laptop uses real data (a hosted database, the user's real account) or a test database: ask, with what the repo shows (`.env` pointing at a hosted URL). Save `"local_real_data": true` or `false`. While it's true (or unset), clicks, typing and page scripts in the browser ask first; looking doesn't
   - frontend checks that apply (responsive layouts, and so on): ask
   - brand kit location: repo first, then ask. Where mockups go: Claude artifacts unless the project differs (a company that doesn't allow them: local HTML)
   - generated files the changed-files check should skip (coverage, snapshots, caches) as globs. With Serena, add `.serena/**`: Serena writes its project file there on its first start in each repo. A glob for a folder git already ignores isn't needed (setup save says so)
   - this project's own risky files, beyond the built-in ones (auth, sessions, permissions, payments, billing, checkout, invoices, migrations, `.sql`, infra, deploy and CI config, dependency manifests): ask, with suggestions from the repo, such as money math (pricing, ledger, wallet, tax), user data and exports, webhooks, crypto and key handling, feature flags, and shared code most of the repo imports (SocratiCode's graph shows it). Save the ones the user picks as `risky_paths` globs (`src/ledger/**`, `lib/money.ts`): a change to one outside the approved plan is then refused, and a plan that changes one can't be small. None: leave it out
   - whether to keep a glossary and decision records
3. Review CLAUDE.md, WORKFLOW.md and similar files against the real code. List what's outdated, repeated, or in conflict with Plumbline, with the change you'd make. Don't offer to apply them now: edits wait for a task, so offer one at the end ("start a task to fix these docs?").
4. Try the commands before saving, so the setup is saved once: run each one as it is (`npm test`, `npm run lint`, ...); outside a task they run under Claude Code's own permission mode. Note how long the full suite took (`suite_seconds`). If one fails, re-check the repo and propose the fix; don't guess. Run a check that reaches the network (`npm audit`) once.
5. Save, once, at the end. Personal projects get `.plumbline.json` committed in the repo; company projects keep it on this laptop only. Write the JSON and save it in one step (a confirm prompt appears; the user checks the commands, since saved commands are what Claude may run before approval):
   ```
   plumbline setup save <<'JSON'
   {"kind": "personal", "base_branch": "main",
    "commands": {"test": "...", "test_related": "... {files}", "lint": "...", "build": "...", "app": "...", "db_up": "...", "e2e": "...", "format": "...", "typecheck": "...", "security": "...", "builder_setup": "..."},
    "ignore_changes": ["coverage/**"], "risky_paths": [], "frontend_repo": "", "deploy_notes": "", "prod_access": "tunnel",
    "deploy_pipeline": true, "local_real_data": true, "frontend_checks": [], "brand_kit": "", "mockups": "artifacts", "glossary": false, "suite_seconds": 25}
   JSON
   ```
   Only include commands that exist. If an MCP server this project uses has tools that only read but whose names don't say so (Playwright's `browser_navigate`, `browser_snapshot`), list them as `"mcp_read_tools": {"<server as in mcp__<server>__tool>": ["browser_navigate"]}`: until then they count as changes and wait for the approved plan. Serena's are known already. A tool whose name says write stays a write. The challenger, the reviewers and the Jira checks are on by default; to switch one off for this project, add it to `"parts"`: `"challenger": false`, `"reviewer": false` (all reviews), one reviewer by name (`"security-reviewer"`, `"data-reviewer"`, `"ux-reviewer"`, `"plan-reviewer"`), `"jira": false` (the ticket read and the drafted comment), `"design": false` (the design workflow's direction pick) or `"devops": false` (the per-command confirm for deploys, deletes and production writes in the approved plan, and the refusal of deploys by hand; the basic prompt for outside-the-laptop commands stays on), and say what that gives up. `tests_ran_pattern` (a regex with a `(?P<ran>\d+)` group, and optionally `(?P<failed>\d+)` and `(?P<skipped>\d+)`) is only needed if `plumbline run test` says it couldn't tell how many tests ran. The e2e command is what the finish check runs for changes that reach the frontend. When `format`, `typecheck` or `security` is saved, every commit needs it to pass (or have no more problems than before the task). The format command only checks and must fail when a file isn't formatted: `prettier --check .`, `ruff format --check`, `black --check .`, `test -z "$(gofmt -l .)"` (plain `gofmt -l` always exits 0); one that rewrites (`--write`, `-w`, `black .`) is refused. A security scan that reaches the network (`npm audit`) is the user's call. A test run whose database, queue, cache or mail settings point off the laptop is refused; if a setting like that is there but the tests never connect to it (a hosted database the unit tests mock), the user can list its name in `"test_targets_ok": ["DATABASE_URL"]`. Ask before adding one. `builder_setup` runs in each new builder copy (a copy has only the files git tracks, so no `node_modules`), for example `pnpm install --frozen-lockfile --prefer-offline`, `npm ci --prefer-offline`, `uv sync --frozen` or `bundle install --local`; it must install into ignored folders only (Plumbline puts back any tracked file it changes) and finish within 150 seconds. Leave it out if installing is slow; the lead then runs the tests after merging. Tests named in a way Plumbline doesn't know (it knows `*_test.go`, `*.test.ts`, `test_*.py`, `*_spec.rb`, `tests/`, Rust `tests.rs`, `FooTest.java`, `FooSpec.scala`, ...) go in `"test_files": ["*.check.ts", "checks/"]`, so blind QA can write them.
6. **Claude Code's Bash sandbox** (optional, this checkout only): ask whether to turn it on, with these pros and cons. First check `git ls-files .claude/settings.local.json`: when that file is tracked, `plumbline setup sandbox` refuses (the file would carry this laptop's sandbox settings into git). Say so when you ask: the way out is to untrack it and add it to `.gitignore`, which is its own small task for the user to OK. If yes, run `plumbline setup sandbox` (add `--exclude psql` or the project's database client, so its connections work; a confirm prompt appears). It writes `.claude/settings.local.json` (the file Claude Code's `/sandbox` panel uses), keeps it out of git, and `plumbline setup undo-sandbox` takes out only what it added. `plumbline status` shows whether it's on.
   - Pros: commands Claude runs directly can't read or change Plumbline's folder (the seal key, task state, proof, helpers' notes), so they can't forge proof, and they can't write outside the project.
   - Cons: Plumbline's own commands, Docker and the excluded database client run outside it, and so does the code they start (the test suite, proof commands, a container with a mounted folder). Package registries and other hosts must be allowed by domain (`sandbox.network.allowedDomains`). Caches outside the project need `sandbox.filesystem.allowWrite`. Dev servers may need `sandbox.network.allowLocalBinding`, and e2e browsers may not start. Logins (gh, keychain, aws sso) may need extra settings. Linux needs bubblewrap and socat; native Windows isn't sandboxed. Failures don't say "sandbox". With it on, each plumbline command runs on its own line (a pipe, redirect, heredoc or `&&` can keep the line sandboxed, where Plumbline can't save proof), so save the setup from a JSON file written outside the repo (`plumbline setup save --file <path>`) instead of a heredoc.
7. First time in this project: index it in SocratiCode to 100% and turn on its file watcher, and do one Serena lookup to confirm it works for the project's languages. If a language server needs installing, ask first.

End with a short summary: what's ready, what the user still needs to do, and anything that looked off.
