# Task workflow

Task: $ARGUMENTS

Hooks enforce the gates. Your job is the thinking: dig in fully, miss nothing, stay on the task, prove the result. If you got something wrong at a checkpoint, go back a step instead of pushing on.

## 1. Read the task
- Jira ticket: read the ticket and every comment with the Jira tools (comments often change the requirements); company tasks on a ticket can't reach the checkpoint without it. List any attachment you can't open by name and ask the user to share it. Never guess what an image shows. Pass the ticket to `plumbline task start --ticket`.
- The user's own words: if vague, ask all your questions in one message, each with a suggestion.

## 2. Check the setup
- `plumbline status`. No setup: stop and suggest /plumbline:setup.
- Check MemPalace, SocratiCode and Docker once, in parallel (Serena and Context7 too if the task needs them). One fix attempt each, then ask the user. A required tool that's down means the task doesn't start.
- Start the task right away, without asking the user first (starting changes nothing; the plan question is their one stop): `plumbline task start --title "..." --ticket ... --size small|normal|big --why "..."`. Run it on its own line (no `&&` with other commands), so the task is tied to this session. Size is impact, not lines: say why. Small means low impact: a rename, a typo, a local fix. Never small: a change to how often or how much the app talks to a server or what runs in the background (retries, polling, timers, caching), even one number. A file on the setup's risky list (shared helpers, money math) can still be small when the change can't reach its behaviour: say why in --why. The checkpoint never accepts "small" for the built-in high-impact kinds (auth, permissions, payments, migrations, deploy, dependencies, security code: the user can keep one small by typing /plumbline:size small; never suggest it) or for files that decide which checks run (CI, git hooks, test or lint config, AI instructions); change it with `plumbline task size normal --why "..."` (only before approval).

## 3. Check the code
- SocratiCode finds where to look and what depends on it. Serena finds every exact caller and definition. MemPalace answers "have we seen this before?" (never facts about the code).
- Open the real files before quoting them. Every file:line you write must be a file you opened in this task (Read, or `cat`/`sed -n`/`head`/`grep -n`/`rg -n` printing it to you, not piped into `wc` or captured); a helper's reads don't count for you.
- Big or many-part code to trace: start tracers (`subagent_type: plumbline:tracer`, several at once, one part each, in the background). Give each the part and your own file:line findings to check. Their reports (`trace-N.md`) point you to the lines; open what you quote.
- Check the ticket against the code. Note anything outside the ticket (a bigger problem, the same bug elsewhere).
- Reuse: search for code that already does the job (a helper, validator, query or component), by the idea rather than the ticket's words, and past the files you already have open. Write the searches and what they found under `## Reuse` in understanding.md; the checkpoint is refused without it.
- For library questions, Context7 for the exact versions in the lockfile, then the web. Never send company code, ticket text or names.
- Bugs: reproduce first: `plumbline run test`, one test file or a script that only looks all run before approval. The `plumbline run` runs before your first edit are the task's starting point (the one with the fewest failures counts), so failures that were already there won't block you later.
- Package changes (a manifest or lockfile in `## Files`, or an install in "Needs your OK"): run `plumbline run test` (and every other saved check: lint, build, format, typecheck, security) before the checkpoint, so the same commands can be compared after; the checkpoint is refused until then.

## 4. Make the plan (no stop yet)
The user usually hands over the task and comes back later, so research and plan in one go.
Small task: write only `plan.md`: what changes, with file:line; `## Files` naming each file; `## Cases` linked to tests. No understanding.md, no proof or "Needs your OK" sections unless they apply. Normal and big: write `understanding.md` and `plan.md` in the notes folder (`plumbline docs-dir`) with the Write tool, using [checkpoints.md](${CLAUDE_PLUGIN_ROOT}/skills/task/checkpoints.md): what changes and where, `## Files`, `## Cases` linked to tests (`[failure]` and `[concurrent]` cases where a dependency can fail or two runs can overlap), `## Real-world proof`, `## Needs your OK` (packages, outside-the-laptop commands), the checks, the branch, and which helpers will run. Every line decides something: "TBD" or "handle edge cases" is refused. Real choice on a big task: recommend one approach and plan it in full, with the others in a few lines each so the user can pick at the same stop.
If the task is so unclear that planning would likely be wasted, ask your questions first (one message, each with a suggestion), or use the optional `Checkpoint 1` for the understanding alone.

## 5. The challenge (skip for small tasks)
- Once both files are written, start the challenger: the Agent tool with `subagent_type: plumbline:challenger`. Tell it the task in one line; Plumbline gives it the notes folder and its findings file. It reads, attacks both files, and writes `challenge-1.md`.
- Check each finding against the code before acting on it. Fix what holds up in understanding.md and plan.md; push back on the rest with evidence.
- A second round only if the first changed the plan a lot (at most 2).
- Add `## Challenge note` to plan.md: what was questioned, what changed, and anything you disagreed with and why. The checkpoint is refused without it and without a finished challenger run.
- It runs without the user, so it adds no stop. Small tasks, or a project with `"parts": {"challenger": false}` in its setup, skip it.

## 6. The checkpoint
AskUserQuestion with header `Checkpoint`, options `Approve`, `Change something` and `Drop it` (Drop it closes the task). First show the plan in the chat as a message (not a file), as checkpoints.md's "The plan in chat" shows: the goal first, then plain sections with Title Case headings and full sentences, and the technical details left in plan.md (its path on the last line, the only path shown). No task ids or Plumbline steps. The question itself carries the problem, the fix and the risk in two or three short sentences, since it can cover the chat. Never pre-answer it.

## 7. Decisions vs common sense
- A real decision is asked right away, with options and your recommendation: a trade-off ("fixing this changes that"), a choice between approaches, anything that changes behaviour the plan didn't cover.
- Common-sense calls go ahead and are listed in the report: a test helper in the same module, formatting a file you touched, a generated file.

## 8. Build and prove
- Branch per [git.md](${CLAUDE_PLUGIN_ROOT}/skills/task/git.md). Uncommitted changes when switching branches: stop and ask.
- Before the first change (after any branch switch): `plumbline run checks`. It runs and records every saved check (test, lint, build, format, typecheck, security) on the approved code. These runs are the starting point, so a check that already failed doesn't block the finish. The first edit is refused until then, and builders and blind QA start editing only after them.
- Big tasks: blind QA first, before any code change. Start `subagent_type: plumbline:qa` right after the checkpoint; it writes tests from `## Cases` without seeing the new code (`qa-N.md`). While it runs, your own code edits in this checkout are refused: build through builders meanwhile, or wait. If the code already changed, the user decides whether to waive it (`plumbline waive qa`). In the report's `## Review`, say what QA's tests caught. If the code's shape moved under a QA test, you may fix its setup (a constructor, an import), never what it expects, and name the file on the Weakened tests line; reviewers compare it with QA's version.
- To look at a builder's work, stay in the main checkout: `git -C <its copy> diff`, `plumbline builder list`. Never `cd` into its copy (the shell stays there, and merging, checks and proof run from the main checkout).
- Independent parts of the plan can go to builders (`subagent_type: plumbline:builder`), one per part, at the same time. Each gets its own copy of the repo made from your code as it is now, so start them after anything they build on is in place. Give each its part, the plan's files and cases for it, what it uses from other parts and what it hands them, and your file:line notes; pass `model: sonnet` for simple, clear parts (the plan says which), and leave the session's model for tricky or risky ones. When a builder stops, read its `build-N.md` and its `## Status` (done, done with concerns, blocked, needs context: Plumbline won't merge the last two; drop the copy and give the part what it lacked, or do it yourself), check its work, then `plumbline builder merge <n>` (refuses overlapping edits and writes nothing then: bring those parts over yourself, then `plumbline builder drop <n>`). The finish check needs every copy merged or dropped. Small tasks: build it yourself.
- A failing test first (it fails because of the bug), then the fix, then a test for every case. For each `[bug]` case, run its test with `plumbline run related --files <test>` and see it fail while only tests have changed since approval: the finish check needs that recorded failing run, of the test as it is at the end (edit the test later, and it must be seen failing again). If the fix came first, set the changes that aren't tests aside (`git stash push --include-untracked -- <files>`), run it, then `git stash pop`. If it can't fail without the fix, ask the user, who can waive it (`plumbline waive bug-test`). Follow [playbooks.md](${CLAUDE_PLUGIN_ROOT}/skills/task/playbooks.md) for bugs, refactors and performance. Tag temporary debug logs `[PLB-DEBUG]`; the finish check refuses while one is left.
- While building: `plumbline run related --files <changed files>`. Near the end: `plumbline run checks` (every commit needs each saved check), and `plumbline run related --files <the case tests>` when the suite's output doesn't name them: each case's test must have run and passed on the final code, with none skipped. A change that reaches the frontend (frontend files, or an API change in a project with a frontend): start the local database, backend and frontend, then `plumbline run e2e`; the finish check needs it when the setup saves an e2e command. A test run aimed at a database or service off the laptop is refused: point it at a local one in `.env.test`. A long suite can go to the tester (`subagent_type: plumbline:tester`) in the background while the reviewers work; its runs are recorded like yours.
- Real-world proof for each kind in the plan, after the last edit. The output must show the intended change (the response body, or the record after the call), not only a status code: a 200 can come from the wrong code path. `plumbline run proof api -- curl -s -i -X POST http://localhost:.../orders/42/refund` (prints the status and the body), `plumbline run proof ui -- npx playwright test ...` (or, with Claude in Chrome: open the changed screen in the local app and take a screenshot after the last edit; Plumbline records that as the ui proof. A unit test or fetching a file isn't ui proof. When the app uses real data, clicks and typing ask the user first), `plumbline run proof schema -- psql "$LOCAL_DB" -c "..."`.
- Build to the end without waiting on the user. Files outside the plan that belong to the same change are fine (list them in the report). Risky files outside the plan and the user's unsaved work are refused: keep going, and put them under "For you". Packages and outside-the-laptop commands only if listed in "Needs your OK".
- Outside the laptop (devops): list the exact commands in "Needs your OK", dry run first where there is one, and a backup check before any database change outside local. Deploys, deletes, production writes and commands on other machines still show the user a confirm prompt each time, so do everything else first and run them together near the end. A project whose pipeline deploys never deploys by hand. Looking at production or the cloud (a cloud CLI's list/get/describe/logs, `gh pr view`, a `psql -c "select ..."`) runs without a prompt; anything that changes something there, or prints a secret, asks. The setup's `prod_access` says how to connect.
- UI changes: phone first (about 360px wide, no sideways page scroll, finger-sized tap targets, nothing that depends on hover), and the setup's `frontend_checks` in the plan's checks. New or changed screens that need a look agreed first: that's the design workflow (/plumbline:design).
- A real decision (see step 7) is asked right away. Before any stop, finish what doesn't depend on the answer.
- Requirements change mid-task: `plumbline task replan`, update plan.md, ask the checkpoint again. Unrelated: suggest a separate task.
- 3 failed fix attempts: stop, say what you tried and learned, and give options.

## 9. Review
- After the proof passes, start every reviewer in the plan's `## Team` at once, in the background: the Agent tool with `subagent_type: plumbline:code-reviewer` (always; a small task gets only this one, plus the security reviewer for security code), `plumbline:plan-reviewer` (normal and big tasks), and `plumbline:security-reviewer`, `plumbline:data-reviewer`, `plumbline:ux-reviewer` where the files call for them. Plumbline gives each the notes folder, the diff base (the commit the task started from), the shared checklist and its findings file (`code-review-1.md`, ...). The finish check names any you missed, including a specialist called for by a file changed outside the plan.
- Give each reviewer the task in one line. Never pass one reviewer's findings to another: each review stays independent.
- Reviewers list every finding with a score. Check each one at 80 or more against the code before fixing; fix the must-fix ones that hold up, and fix or list each should-fix (the report's "Should-fix not fixed" line). Under 80: open what you can confirm cheaply and fix what holds up; the report lists them one line each. To push back on one, write it with your evidence to `<reviewer>-disputes.md` in the notes folder (`code-reviewer-disputes.md`, ...), then run that reviewer again: it answers each dispute, withdrawn or upheld. An upheld finding is the user's call: put it under "For you" (say "upheld", with both sides).
- After fixes, re-run the related tests (and the full suite, lint and build if the fix touched more), then every reviewer again: the finish check needs each one's review of the code as it is now. Tell each what changed since its last run. At most 3 runs per reviewer (the first plus 2 fix rounds); still not clean after that, or it's a trade-off: it goes to the user.
- While reviews run in the background, wait for them; don't end with "done" meanwhile.
- A project can switch reviews off in its setup (`"parts": {"reviewer": false}`, or one reviewer by name).

## 10. Report, then the user decides
Write `report.md` after the last review (format in checkpoints.md). The finish check needs `## Verdict` (Ready, Ready with noted limitations or Not ready, then a `Rollback:` line), `## Review` (with "Should-fix not fixed:" when a reviewer marked any), `## Common-sense calls`, `## For you`, and every waiver under Proof. A check that couldn't run is written "couldn't run", with why and the exact command to run later in backticks, never "skipped"; that, a waiver or an upheld finding rules out plain Ready. The "Weakened tests:" line names each file the diff weakens, with why (the finish check lists any it finds). Then a short chat version, the way rules.md's "Talking to the user" shows: one sentence on what changed (a failure or something left out comes first), the checks and the review in a line each, and a "For you" line ("For you: want me to commit it?"); when "For you" holds something more, the message opens with it. No paths, task ids or Plumbline steps. The finish check sends back a closing message without it. Then ask whether to commit (and, where it applies, mention the user pushes). Commit only after they say so; the commit hook checks the proof. Then `plumbline task finish`, after the commit: it refuses while the task's changes aren't committed, because once the task is done nothing can be committed for it. If the user says they'll commit the changes themselves, run `plumbline task finish --uncommitted` (it asks them).

Jira ticket: write the comment to `<TICKET>-jira-comment.md` in the notes folder (`TICKET-123-jira-comment.md`): only the comment, a few plain lines a teammate reads in seconds, ready for the user to copy, check and post. No AI markers, no em dashes. Put the suggested status in the report under "For you". Don't post it: Jira is draft-only, unless the user's own message asks you to post, and then they confirm the exact text.
